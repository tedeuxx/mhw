````markdown
## The ask

The owner, verbatim:

> «temos que de alguma forma alem de ter algum teste no ci para efetividade de skills antes de publciar nova versao do mhw para uso, temos tbm que ter ao longo do runtime deixar logado alguma informacao de efetividade de subagents para podermos retroativamente melhorar progressivamente no mhw. achoq ue o issue tracker pode ser o local onde temos essa informacao acredito.»

In English, the owner asks for two things. First, a CI test of skill effectiveness that runs before a new mhw release is published for use. Second, subagent effectiveness information logged during runtime, so that the method can be improved progressively in hindsight. He suggests the issue tracker as the place for it.

## What already decides parts of this

- **Commandment 8 has an instrument, but nobody uses it.** `method/scripts/worklog-contract/event.schema.json` (lines 25–34 on rc/next) defines a numbers-only `usage` record (model, effort, tokens, credits), and `mhw worklog prepare-event` produces it. Measured on #512–#524: **0** `worklog-event:v1` events and **0** `usage_provenance`. That includes every slice this session delivered. What is missing is not a writer. It is use of the writer that exists.
- **Review cost per PR is already derived.** `method/skills/sprint-retrospective/SKILL.md`, *"Review cost per PR — rounds and a wall-clock ceiling, from the same markers (#138)"*, already derives gate rounds, lens rounds and wall-clock time from the column-0 markers.
- **One premise of #304 has changed.** #304, the behavioural evaluation of the plugin, was closed NOT_PLANNED on 2026-08-24 because `claude plugin eval` was early access (CLI 2.1.241). On CLI 2.1.329, `claude plugin eval init --bare --eval-dir evals discovery` exits 0 and scaffolds a suite. Running an eval calls a model, so a run was **not** measured.
- **ADR-0005 does not forbid effectiveness logging**, because it governs detection records. It does exclude one tempting metric: counts of firewall interventions by category.
- **No hook may produce this data.** "Hooks only for existential risk" (ADR-0035) rules that out, so the data must be derived or produced by instruction.
- **The retrospective cannot consume this data yet.** mhw switches to scrum (#522, PR #526), and the retrospective only runs at the close of an iteration, so it can consume the data once that lands.

## Intake: agents-lead (loop lane)

Read against `origin/rc/next` at `7557b5193b7c2a16ca5dc011a7534c6c7d3f27ba` on 2026-11-20.

**Scenarios, ordered by cost:**
1. **A model-graded eval as a release gate turns noise into red or green.** It is non-deterministic; that is why `--runs` and `--threshold` exist. (Hypothesis: not measured, because a run is paid.)
2. **Model-graded evals in CI need a secret and paid use.** The overlay grants no paid API use, and writing a secret is the owner's act.
3. **A structural eval proves less than its name.** It proves that references resolve and that renders match. It does not prove that a skill triggers or that it helps. Calling it "effectiveness" would be a green that does not prove what it says.
4. **A naive marker reader inflates reversals.** Measured on PR #518: a gate body mentions `REQUEST-CHANGES` in prose under an `APPROVE-AND-MERGE` literal. Read the literal from the envelope's second line only.
5. **Self-attestation.** `usage` is self-reported. Gate and lens markers are written by a model in a different context. Owner comments are the only human signal, and git (reverts, reopened Issues) is the only objective one. Every metric must name its provenance.
6. **Leakage.** An effectiveness record carries zero free text: only numbers, enums and URLs to the repository's own tracker.
7. **Tracker noise.** A comment per dispatch would add about 3–8 per PR. A derived report adds none.
8. **Not measurable, so out of scope:** findings per lens and mutants killed.

**Design (proposed):**
- **Slice 1.** A read-only `mhw effectiveness report --repo <o/r> --since <date>`, producing deterministic JSON per PR from the tracker and git. It reuses the retrospective's column-0 reader. No ADR is owed for this slice, because it extends #138 in-pattern.
- **Eval layer A.** A structural, deterministic eval in CI, named for what it proves.
- **Eval layer B.** `claude plugin eval` with ablation. An ADR is owed if it is adopted.

## Open owner decisions

- **D1: model-graded eval and paid use.** The options are: never; run locally by the owner before the release candidate, informative only; or in CI, blocking the release candidate. The intake recommends local and informative.
- **D2: where the aggregate lives.** The options are: tracker comments only; raw data stays on the tracker and the aggregate goes to a repository file generated on demand; or a repository file only. The intake recommends raw on the tracker with the aggregate in a file.

Until the owner answers, this Issue does not get `ready`.

## Acceptance criteria

- `mhw effectiveness report` reads one repository's merged PRs and closed Issues over a window and prints deterministic JSON per PR:
  - gate rounds and lens rounds, using the column-0 reader shared with sprint-retrospective;
  - each round's verdict literal, read from the envelope's second line only;
  - merge reverts detected in git, and reopened Issues;
  - owner authorization URLs;
  - the summed worklog `usage`, with coverage marked partial where it is absent.
- It writes nothing to the tracker and carries no free text: only numbers, enums and URLs.
- Each metric names its provenance: git (objective), owner comment (human), gate or lens marker (model, cross-context), worklog usage (self-reported).
- Firewall interventions are never counted (ADR-0005).
- A test feeds a marker body that mentions REQUEST-CHANGES in prose under an APPROVE-AND-MERGE literal, and asserts zero reversals. The test goes red under the substring-reader mutation.
- The skills CI eval implements what D1 decides, and is named for what it proves.
````
